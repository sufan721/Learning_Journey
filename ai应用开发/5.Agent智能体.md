# Agent（智能体）— 让 AI 自己动手做事

LLM 会聊天，但只会聊天。你问它"今天几号？"它会编一个。你需要的是一个能**查日历、调 API、搜网页、写文件**的 AI——这就是 Agent。

---

## 一句话理解 Agent

> **Agent = LLM + 工具 + 循环决策**。它不再是一问一答的聊天机器人，而是一个能**感知环境 → 制定计划 → 调用工具 → 观察结果 → 继续行动**的自主实体。

```
传统 LLM：
  用户问 → LLM 答 → 结束

Agent：
  用户给目标 → LLM 想"我需要什么工具？"
            → 调用工具A → 拿到结果
            → 判断"够了吗？还要什么？"
            → 调用工具B → 拿到结果
            → 判断"够了" → 整理输出 → 结束
```

---

## Agent 的四大核心组件

| 组件 | 做什么 | 例子 |
|------|--------|------|
| **LLM（大脑）** | 推理、规划、决策 | GPT-4o / Claude |
| **工具（手）** | 执行具体操作 | 搜索、读写文件、调 API |
| **记忆（笔记本）** | 记住上下文和历史 | 对话历史、向量数据库 |
| **规划（思维框架）** | 拆解任务、多步执行 | ReAct、Plan-and-Execute |

## Agent 的核心循环

一个 Agent 运行时，内部就是一个 while 循环：

```python
# Agent 核心逻辑（伪代码）
def agent_loop(user_goal):
    memory = [{"role": "user", "content": user_goal}]
    
    while True:
        response = llm.chat(memory, tools=[search, calculator, send_email])
        
        if response.has_tool_call():
            # LLM 决定调用工具
            for tool_call in response.tool_calls:
                result = execute_tool(tool_call)
                memory.append(tool_call)
                memory.append({"role": "tool", "content": result})
            # 继续循环，让 LLM 看到结果再决策
        else:
            # LLM 认为任务完成，给出最终回复
            return response.content
```

**关键点**：每一步工具调用后，LLM 都能看到结果，然后决定下一步做什么——这个"观察→决策→行动"的循环就是 Agent 的本质。

## 主流 Agent 设计模式

### 1. ReAct（推理 + 行动交替）

最经典的 Agent 模式。LLM 每一步都输出：**Thought → Action → Observation**，循环直到完成。

```
用户: "旧金山今天的温度是多少华氏度？"

Thought: 我需要知道旧金山今天的天气，先搜索一下
Action: search("San Francisco weather today")
Observation: "San Francisco today: 68°F, partly cloudy"

Thought: 搜索结果已经给出了华氏温度，可以直接回答
Answer: "旧金山今天的温度是 68°F（约 20°C），多云。"
```

### 2. Plan-and-Execute（先规划再执行）

适合复杂多步骤任务。先列完整计划，再逐步执行：

```
用户: "帮我调研三个 AI 框架的优缺点并写成报告"

Plan:
1. 搜索 LangChain 的优缺点
2. 搜索 LlamaIndex 的优缺点  
3. 搜索 Semantic Kernel 的优缺点
4. 对比分析三个框架
5. 生成 Markdown 报告
6. 保存到文件

Execute: 逐步执行 1→2→3→4→5→6
```

> 💡 Plan-and-Execute 对大任务更可控，但灵活性不如 ReAct。实际产品通常是两者混合。

### 3. Multi-Agent（多智能体协作）

多个 Agent 各司其职、互相通信：

```
用户: "开发一个登录页面"

协调 Agent:
  → UI Agent: "设计登录表单 UI"
  → 后端 Agent: "实现登录 API"
  → 测试 Agent: "写测试用例"
  → 审查 Agent: "代码审查"
  → 协调 Agent: 汇总结果，解决冲突
```

## 主流 Agent 框架对比

| 框架 | 语言 | 特点 | 适合 |
|------|------|------|------|
| **OpenAI Agents SDK** | Python | OpenAI 官方、轻量、直接 | 深度绑定 OpenAI 的应用 |
| **LangChain / LangGraph** | Python/JS | 生态最大、工具链全、学习曲线陡 | 复杂 Agent 系统 |
| **CrewAI** | Python | 多 Agent 角色扮演、上手快 | 多 Agent 协作场景 |
| **AutoGen (微软)** | Python | 微软出品、多 Agent 对话 | 企业级多 Agent |
| **Dify / Coze** | 低代码 | 拖拽式搭建 Agent | 不想写太多代码 |
| **Anthropic Tool Use** | Python/TS | Claude 原生工具调用、无需框架 | 简单 Agent、Claude Code 类应用 |
| **Smolagents (HF)** | Python | 极简、代码生成式 | 研究、轻量场景 |

### 选型建议

```
简单 Agent (1-2个工具)    → 直接用 SDK 的 Tool Use，不需要框架
中等 Agent (多工具+规划)   → LangGraph 或 OpenAI Agents SDK
多 Agent 协作              → CrewAI 或 AutoGen
快速原型/低代码            → Dify
绑定 Claude               → Anthropic SDK 原生 Tool Use
```

## 自己做一个最简单的 Agent

不用任何框架，30 行代码就能理解 Agent 的本质：

```python
import json
from openai import OpenAI

client = OpenAI()

# 定义工具
def get_weather(city: str) -> str:
    """查询城市天气"""
    # 模拟返回
    return f"{city}：晴，25°C"

# 工具注册表
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名"}
                },
                "required": ["city"]
            }
        }
    }
]

# Agent 循环
messages = [{"role": "user", "content": "北京和上海的天气分别怎么样？"}]

while True:
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=messages,
        tools=tools
    )
    
    msg = response.choices[0].message
    
    if msg.tool_calls:  # LLM 要调用工具
        for tool_call in msg.tool_calls:
            args = json.loads(tool_call.function.arguments)
            result = get_weather(**args)
            
            messages.append(msg)  # 模型的工具调用请求
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": result
            })
        # 继续循环，让 LLM 看到结果
    else:  # LLM 直接回复，任务完成
        print(msg.content)
        break
```

## Agent 的常见坑

| 坑 | 表现 | 应对 |
|----|------|------|
| **死循环** | LLM 反复调同一个工具，永远到不了终点 | 设 `max_iterations`（如 10），超限强制终止 |
| **选择错误工具** | 该搜索时去算数学，该算数学时去发邮件 | 工具描述写的越清楚越好，在 System Prompt 里加规则 |
| **目标漂移** | 做着做着跑偏了，忘了最初用户要什么 | 在每次循环的 Prompt 里重申初始目标 |
| **上下文爆炸** | 多轮工具调用后 Token 超限 | 中间结果做摘要，删除无用的工具返回 |
| **幻觉调用** | 编造不存在的工具参数 | 工具描述中明确参数格式和允许值 |
| **权限越界** | Agent 删了不该删的、买了不该买的 | **永远分权限级**：读操作自动、写操作确认、危险操作禁止 |

---

## Agent 安全三原则

```
🟢 读操作（搜索、查询、读取文件）   → 自动执行
🟡 写操作（修改文件、发送消息）      → 需要用户确认
🔴 危险操作（删除、付费、发邮件）    → 需要用户二次确认
```

---

## 一句话总结

> **Agent 就是给 LLM 装上了手和眼睛，让它自己发现"不够" → 动手获取 → 判断"够了" → 再回答你。**

它不是魔法，只是一个设计精良的 while 循环。理解这个循环，你就理解了 Agent 的全部。
