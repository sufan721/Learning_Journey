# Prompt Engineering — 让 LLM 稳定输出你想要的结果

LLM 就像一个能力超强但脑子一根筋的实习生——你说的越清楚，他干的越好。**Prompt Engineering 就是"学会给 AI 下达正确的指令"。**

---

## 一句话理解

> **Prompt Engineering** 不是写提示词的玄学，而是**通过结构化输入来控制 LLM 输出质量**的工程方法。

---

## Prompt 的基本结构

一个合格的 Prompt 通常包含以下要素：

```
┌─────────────────────────────────┐
│ 1. 角色设定      │ System Prompt │  → "你是谁"
│ 2. 任务描述      │               │  → "做什么"
│ 3. 上下文信息    │               │  → "背景是什么"
├─────────────────────────────────┤
│ 4. 输入数据      │ User Message  │  → "原材料"
│ 5. 输出格式      │               │  → "怎么交给我"
│ 6. 约束和边界    │               │  → "不能做什么"
└─────────────────────────────────┘
```

### 一个对比例子

**❌ 坏的 Prompt：**
```
帮我写一个函数
```

**✅ 好的 Prompt：**
```markdown
你是一个资深 Python 后端工程师。

任务：写一个函数，接收用户ID列表，批量查询数据库返回用户名。

要求：
- 使用 async/await
- 参数和返回值都要有类型注解
- 批量大小不超过 100 条
- 用 pydantic 做数据校验

不要生成测试代码。
```

## 六大核心技巧

### 1. 角色扮演（Role Prompting）

最基础但最有效的技巧。明确角色，模型会调用它理解的那个角色的知识模式：

```
❌ "解释一下 CAP 定理"
✅ "你是一个教了 15 年分布式系统的大学教授。用大一新生能听懂的语言解释 CAP 定理，举 2 个生活中的例子。"
```

常用角色模板：
```
你是一个 [角色]，拥有 [经验/技能]。
你的任务是 [做什么]。
```

### 2. 少样本提示（Few-Shot Prompting）

给模型看 2~3 个"问题→答案"的范例，它会直接照搬你的格式和风格：

```markdown
把用户的自然语言转成 JSON 格式。

示例1：
输入："下周三下午3点开会"
输出：{"action": "create_event", "title": "开会", "time": "2026-08-05T15:00:00"}

示例2：
输入："明天早上9点提醒我买菜"
输出：{"action": "set_reminder", "title": "买菜", "time": "2026-08-01T09:00:00"}

现在请处理：
输入："大后天晚上8点聚餐"
输出：
```

> 💡 1~3 个示例就够，多了浪费 Token。示例的质量比数量重要得多。

### 3. 思维链 (Chain-of-Thought, CoT)

让模型**一步步想，而不是直接给答案**。对推理、数学题、复杂的逻辑判断效果显著：

```
❌ "甲比乙大3岁，乙是丙年龄的2倍，丙今年10岁，甲几岁？"

✅ "甲比乙大3岁，乙是丙年龄的2倍，丙今年10岁，甲几岁？
     请你一步一步推导。"
```

更高级的变体 — **Zero-shot CoT**，加一句 "Let's think step by step" 就够了。

### 4. 结构化输出 (Structured Output)

不让模型自由发挥，而是**规定输出格式**：

```markdown
请分析以下代码的问题，**严格按 JSON 格式输出**：
{
  "issues": [
    {
      "severity": "high | medium | low",
      "line": 行号,
      "problem": "问题描述",
      "fix": "修复建议"
    }
  ]
}
```

现在主流模型（GPT-4o、Claude）都支持 **JSON Mode / Structured Outputs**，可以强制模型只输出合法 JSON。

### 5. 拆解任务 (Task Decomposition)

复杂任务不要一次丢给模型，**拆成多步**：

```markdown
❌ 一次： "分析这份合同的风险，提取关键条款，生成摘要，翻译成英文"
    → 输出容易遗漏，质量参差不齐

✅ 拆开：
   第1步： "列出这份合同中的所有风险条款"
   第2步： "对每个风险条款打分（高/中/低）并解释原因"
   第3步： "生成一份 100 字以内的合同摘要"
   第4步： "把摘要翻译成英文"
```

这就是 Agent 的基本思路——用 Prompt Chain 串联多步调用。

### 6. 给它退路 (Guardrails)

明确告诉模型**边界在哪里**——不知道就说不知道，不要硬编：

```markdown
规则：
- 如果你不确定答案，直接说"我不确定"，不要猜测
- 如果用户问的问题超出你的知识范围，拒绝回答并说明原因
- 不要编造数据、链接、引文
```

## Claude/OpenAI 专属写法对比

| 要素 | OpenAI (GPT) | Anthropic (Claude) |
|------|-------------|---------------------|
| 系统提示词 | `role: "system"` | `system` 参数 |
| 输出结构 | JSON Mode / Structured Outputs | Prompt 中 XML 标签约束 |
| 长文档 | Assistant 预填 `{` 触发 JSON | 更适合 Prompt 内嵌 XML |
| 技巧偏好 | 角色扮演 + CoT 效果好 | XML 标签组织上下文效果好 |

### Claude 的 XML 标签技巧

Claude 对 XML 标签特别敏感，用标签把不同内容"隔开"比自然语言效果好得多：

```markdown
<system>
你是一个代码审查专家。
</system>

<rules>
- 只报告真正有问题的代码
- 不确定的不要报
</rules>

<code>
def foo(x): return x+1
</code>

<format>
按以下 JSON 格式输出...
</format>
```

## Prompt 模板管理

不要在代码里到处写字符串！把 Prompt 当成代码一样管理：

### Python 模板示例

```python
# prompts.py
CODE_REVIEW_PROMPT = """
<system>
你是一个{language}代码审查专家，拥有{experience}年经验。
</system>

<task>
审查以下代码，关注：{focus_areas}
</task>

<rules>
{rules}
</rules>

<code>
{code}
</code>
"""

# 使用时
prompt = CODE_REVIEW_PROMPT.format(
    language="Python",
    experience="10",
    focus_areas="安全性、性能、可读性",
    rules="只报告严重和中等问题",
    code=user_code
)
```

### 目录结构建议

```
prompts/
├── code_review.py      # 代码审查相关 prompt
├── data_extract.py     # 数据提取相关 prompt
├── customer_service.py # 客服相关 prompt
└── base.py             # 公共规则（不胡编、格式要求等）
```

## 常见翻车现场

| 翻车 | 原因 | 改正 |
|------|------|------|
| 让 LLM 数单词/数字数 | Token ≠ 字，它不擅长精确计数 | 让它输出后再用代码数 |
| Prompt 里写 "不要做 X" | 模型反而更容易做 X | 写 "只做 Y"，正向约束 |
| 一次塞太多要求 | 模型会选择性忽略 | 拆分步骤 |
| Prompt 太长 | 核心指令被淹没 | 用 XML 标签/分隔符标出重点 |
| 把模型输出直接入库/展示 | 格式可能不符合预期 | 用 JSON Mode + 代码校验 |

## 进阶方向

掌握了基础技巧后，下一步可以深入：

- **自动 Prompt 优化（DSPy）** — 用算法自动调 Prompt，而不是人手试
- **Meta-Prompting** — 让 LLM 自己写 Prompt
- **Prompt 版本管理** — 像管理代码一样用 Git 管 Prompt，做 A/B 测试
- **动态 Prompt** — 根据上下文自动选择或拼接不同的 Prompt 片段

---

## 一句话总结

> **把 Prompt 当成代码写：有结构、有版本、有边界条件、有测试用例。**

Prompt Engineering 的核心不是背"万能公式"，而是养成"站在模型的角度想它会怎么理解这句话"的习惯。你写的每一个词，都要经得起这个角度的检查。
