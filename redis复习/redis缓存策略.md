# Redis 缓存策略

> **金句开篇：** 缓存不是银弹，但没缓存你连弹弓都没有。缓存设计得好，系统岁月静好；设计得烂，凌晨三点准时报警。

---

## 缓存的意义

一句话：**用空间换时间，用成本换体验。**

数据库能扛 3000 QPS，加了 Redis 缓存能扛 100000 QPS。但缓存引入了**数据一致性**这个天大的麻烦 —— 你多了一台 Redis，就等于多了无数个"MySQL 和 Redis 里的数据是不是一样的？"的疑问。

> **批判时刻：** 很多人的缓存思维是："MySQL 扛不住了 → 加 Redis → 问题解决"。但实际上，加缓存是**把问题转移**了——从"数据库撑不住"变成了"缓存和数据库怎么保持一致"。**不加缓存是性能问题，加了缓存是分布式问题。前者死得痛快，后者死得诡异。**

---

## 缓存读写模式

### 1. Cache-Aside（旁路缓存）— 最常用

```
读操作：
  1. 先查 Redis
  2. Redis 有 → 直接返回
  3. Redis 没有 → 查 MySQL
  4. 把结果写入 Redis，返回

写操作：
  1. 更新 MySQL
  2. 删除 Redis 缓存（不是更新!）
```

> **灵魂拷问：为什么是删缓存，不是更新缓存？**
>
> 如果更新缓存：
> - 线程 A 更新 MySQL（x=1）
> - 线程 B 更新 MySQL（x=2）
> - 线程 B 更新 Redis（x=2）
> - 线程 A 更新 Redis（x=1）
>
> **缓存里是 1，数据库里是 2，且这个不一致是永久性的，直到下一次写入。**
>
> 而**删除缓存**的话，最坏情况只是下次读的时候缓存没命中，去 MySQL 取最新的。**删除是延迟修复，更新是永久毒瘤。**

| 方案 | 优点 | 缺点 |
|------|------|------|
| Cache-Aside | 简单，应用层可控 | 代码侵入，需要自己管缓存逻辑 |
| Read/Write Through | 缓存层透明，代码干净 | 需要缓存中间件支持 |
| Write Behind | 写入性能极高 | 丢数据风险，一致性最差 |

### 2. Read/Write Through（读写穿透）

应用只跟缓存打交道，缓存自己负责同步数据库。对应用层透明，但需要中间件支持（Redis 原生不支持，需要自己做一层封装）。

### 3. Write Behind（异步回写）

应用只写缓存，缓存**异步批量**写回数据库。性能最高，但缓存宕机 = 数据丢失。MySQL 的 InnoDB Buffer Pool、操作系统 Page Cache 都是这个思路。

> **骚话：** 大部分中小项目用 Cache-Aside 就够了。别为了"架构优雅"上一套复杂缓存框架，结果出了 Bug 没人看得懂。**过度设计是程序员的自我感动。**

## 缓存三兄弟：穿透/击穿/雪崩

这是面试必问的 Redis 铁三角。很多人背得滚瓜烂熟，但真的在生产环境处理过的人不多。

---

### 一、缓存穿透

**定义：** 查询一个**根本不存在**的数据（id=-1），缓存没有，数据库也没有，但每次请求都打到数据库。

```
每次请求: 客户端 → Redis(查不到) → MySQL(也查不到) → 返回 null
↓
Redis 里永远没有这个值，所有请求全部穿到 MySQL
```

> **实战场景：** 恶意攻击者用 `id=-1,-2,-3...` 批量请求，或者业务上的冷数据（新上线的商品还没入库就被疯狂查询）。

#### 解决方案

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **缓存空值** | MySQL 返回 null，也在 Redis 存一个 null（TTL 设短一点，如 2-5 分钟） | 简单但浪费内存，可能短期不一致 |
| **布隆过滤器** | 把所有合法 ID 存到布隆过滤器，请求先过滤 | 内存极省，但有误判率，且 ID 变化要维护 |
| **参数校验** | 请求入口直接拦截非法参数（id<0） | 最基础最有效，但防不了合法 ID 的查询请求 |
| **限流** | 单个 IP/用户对同一 key 频繁请求就限流 | 防御恶意攻击，但不影响正常用户 |

> **金句：** 缓存穿透是**最容易被忽略**的问题，因为开发时用正常数据测不出来。上线后被人用 `id=-1` 打穿缓存，MySQL CPU 100%，你才意识到什么叫"防御性编程"。**非法参数校验是最低成本的防线，但它救过无数个项目。**

#### 布隆过滤器原理（极简版）

```
布隆过滤器 = 一个超大的 BitMap + K 个 Hash 函数

添加元素 "user_1001":
  Hash1("user_1001") = 3   → setBit(3)
  Hash2("user_1001") = 8   → setBit(8)
  Hash3("user_1001") = 15  → setBit(15)

查询 "user_1001" 是否存在:
  检查 bit[3] && bit[8] && bit[15]
  如果全为 1 → "可能存在"（有误判）
  如果有一个为 0 → "一定不存在"（100% 准）
```

> **一句话总结：** 布隆过滤器说"没有"一定没有；说"有"不一定有。**宁可错杀一千（多查一次 MySQL），也不放过一个（缓存穿透）。**

### 二、缓存击穿

**定义：** 一个**热点 Key** 过期，瞬间大量并发请求同时打到 MySQL。

```
热点 Key "hot_item:stock" 过期
    ↓
10000 个并发请求同时查 Redis（全部 miss）
    ↓
10000 个请求同时打到 MySQL ⚡💀⚡
```

> **批判时刻：** 缓存击穿是小概率但高破坏的事件。你的一切系统都在安稳运行，直到某个秒杀商品的库存 Key 刚好在秒杀开始那一刻过期——这叫"墨菲定律在分布式系统中的完美呈现"。

#### 解决方案（附带代码级实现）

**方案一：互斥锁（Mutex Lock）**

```java
public String getData(String key) {
    String value = redis.get(key);
    if (value != null) return value;

    // 抢锁，只让一个线程去查 MySQL
    String lockKey = "lock:" + key;
    try {
        // SETNX + 过期时间，原子操作
        if (redis.set(lockKey, "1", "NX", "EX", 10)) {
            // 双重检查：可能前面的线程已经写入缓存
            value = redis.get(key);
            if (value != null) return value;

            value = db.query(key);            // 查 MySQL
            redis.set(key, value, "EX", 60);  // 写缓存
            return value;
        } else {
            Thread.sleep(50);    // 没抢到锁，等一会儿
            return redis.get(key); // 重试读缓存（或递归调用）
        }
    } finally {
        redis.del(lockKey);  // 释放锁
    }
}
```

**方案二：逻辑过期（永不过期 + 异步更新）**

```
不要给热点 Key 设物理 TTL！
在 Value 里存一个 "逻辑过期时间" 字段。
读取时：
  - 逻辑未过期 → 直接返回
  - 逻辑已过期 → 先返回旧值，再异步启一个线程去刷新缓存
```

> **骚话：** 逻辑过期是"用空间换时间"的极致体现 —— 热点数据存在 Redis 里就不删了，直到不是热点为止。唯一代价是：你用了一个线程池去做异步刷新。**而线程池炸了的风险，比数据库炸了的风险小一万倍。**

**方案三：提前预热**

在秒杀/活动开始前，手动或脚本把热点数据加载进 Redis，设置一个**超长或不过期的 TTL**。

### 三、缓存雪崩

**定义：** 同一时间**大量 Key 同时过期**，或者 **Redis 宕机**，所有请求打到 MySQL，数据库崩溃。

```
大量 Key 设置了相同的 TTL
        ↓
   TTL 到，集体过期
        ↓
   所有请求打向 MySQL
        ↓
  MySQL 挂了 💀
        ↓
   整个系统不可用 💀💀💀
```

> **批判时刻：** 雪崩的根源往往是**偷懒**——给所有 Key 设了一样的过期时间。代码里写 `redis.set(key, value, 3600)` 的时候从来没想过"如果所有 Key 都在同一秒过期怎么办"。

#### 解决方案

| 方案 | 做法 |
|------|------|
| **TTL 加随机值** | `EX 3600 + random(0, 600)`，最简单有效 |
| **多级缓存** | 浏览器缓存 → Nginx 本地缓存 → Redis → MySQL，层层拦截 |
| **Redis 高可用** | 哨兵/集群，Redis 本身别是单点 |
| **降级限流** | Redis 挂了直接返回默认值/空数据，别把流量放到 MySQL |
| **熔断** | 检测到 MySQL 压力过大，直接熔断，不再穿透请求 |

```java
// TTL 加随机值 —— 最简单又最容易被忽略的银弹
int ttl = 3600 + ThreadLocalRandom.current().nextInt(600);
redis.setex(key, ttl, value);
```

> **金句：** 缓存雪崩的解决方案里，**TTL 加随机值**是最便宜、最有效的。三行代码，能让你睡个安稳觉。但如果你的 Redis 是单机部署，加多少随机 TTL 都救不了宕机 —— **高可用架构是底线，不是加分项。**

### 三兄弟对比速查表

| 问题 | 现象 | 原因 | 经典解法 |
|------|------|------|---------|
| **穿透** | 查不存在的数据，每次都穿到 DB | 缓存和 DB 都没数据 | 空值缓存 / 布隆过滤器 |
| **击穿** | 一个热点 Key 过期，并发打爆 DB | 热点 Key 瞬间失效 | 互斥锁 / 逻辑过期 |
| **雪崩** | 大量 Key 同时过期或 Redis 宕机 | 集体过期 / 单点故障 | 随机 TTL / 高可用集群 |

## 缓存与数据库双写一致性

> **骚话：** 如果你在面试中被问到"如何保证缓存和数据库的一致性"，别直接说"先删缓存再写数据库"——这是送命题。正确回答是：**"没有绝对的强一致性，只有最终一致性和取舍。"**

### 四种双写策略

| 策略 | 做法 | 一致性 | 性能 |
|------|------|--------|------|
| 先删缓存，再写 DB | 删缓存 → 写 DB → 等读请求重建缓存 | **低！** 写 DB 期间其他线程可能把旧数据写回缓存 | 高 |
| 先写 DB，再删缓存 | 写 DB → 删缓存 | 中等 | 高 |
| 先写 DB，再异步删缓存 | 写 DB → MQ/Canal 异步通知删缓存 | 较高 | 最高 |
| 先写缓存，再异步写 DB | 写缓存 → MQ 异步落 DB | **最低，不推荐** | 极致 |

### 推荐方案：延迟双删

```java
// 1. 先删缓存
redis.del(key);
// 2. 写数据库
db.update(data);
// 3. 延迟一段时间（如 500ms），再删一次缓存
Thread.sleep(500);
redis.del(key);
```

**为什么要删两次？**
- 第一次删：清掉旧值
- 写 DB 期间，可能有其他线程读到旧数据写了缓存
- 第二次删：把刚才被污染的数据清掉

> **批判时刻：** 延迟双删不是银弹。`Thread.sleep(500)` 在生产代码里写出来，你的 Leader 会皱眉。更好的做法是：**写 DB 后通过 MQ 异步删缓存**，失败了还能重试。如果要求更高，用 **Canal 监听 MySQL binlog**，由 binlog 驱动缓存更新，做到最终一致性。

### 一致性选型终极指南

| 业务场景 | 推荐策略 |
|----------|---------|
| 用户昵称、头像（一天不改一次） | 先写 DB，再删缓存，重试即可 |
| 库存、余额（高并发读写） | Canal + binlog 异步同步，接受短暂不一致 |
| 订单状态（强一致性要求） | **别用缓存！** 直接读 MySQL 主库 |
| 配置数据（很少变） | 启动时加载到本地内存 + 定时刷新 |

> **终极金句：** 缓存一致性不是一个技术问题，是一个**业务容忍度问题**。你的用户能不能接受 1 秒内看到旧数据？能，那就做最终一致。不能？那就别用缓存，直接查数据库。**在一致性上花的时间，80% 是在解决一个产品经理都不在乎的问题。**

## Redis 内存淘汰策略

当 Redis 内存满了（达到 `maxmemory`），新数据写不进来怎么办？—— **淘汰旧数据。**

Redis 提供了 8 种淘汰策略：

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| `noeviction` | 不淘汰，写请求直接报错 | 你确定内存永远够用？ |
| `allkeys-lru` | 在所有 Key 中淘汰最近最少用的 | **通用缓存，最常用** |
| `allkeys-lfu` | 在所有 Key 中淘汰最不常用的 | 热点数据明显的场景 |
| `allkeys-random` | 在所有 Key 中随机淘汰 | 不太常见 |
| `volatile-lru` | 在设了 TTL 的 Key 中淘汰 LRU | 需要长期保留的 Key 不设 TTL |
| `volatile-lfu` | 在设了 TTL 的 Key 中淘汰 LFU | 同上 + 热点优先 |
| `volatile-random` | 在设了 TTL 的 Key 中随机淘汰 | — |
| `volatile-ttl` | 在设了 TTL 的 Key 中淘汰即将过期的 | 类似"自然淘汰" |

### LRU vs LFU

```
LRU（Least Recently Used）: "你多久没来了？" → 淘汰最久没访问的
LFU（Least Frequently Used）: "你来过几次？" → 淘汰访问次数最少的
```

> **骚话：** LRU 是"最近没人理的滚"，LFU 是"一直没人理的滚"。区别在于：一个刚火的帖子访问频率极高（LFU 保护它），但它可能是昨天发的，今天已经没流量了（LRU 淘汰它）。**选 LRU 还是 LFU，看你的业务是"时效性驱动"还是"热度驱动"。**

### 生产环境推荐

```conf
# 最大使用内存（一定要设！不设的话 Redis 会吃光所有内存）
maxmemory 4gb

# 淘汰策略：通用场景用 allkeys-lru
maxmemory-policy allkeys-lru

# LRU 采样精度（默认 5 够用，设 10 更精确但多耗 CPU）
maxmemory-samples 5
```

> **批判时刻：** 见过最离谱的配置：`maxmemory` 不设，`maxmemory-policy` 默认 `noeviction`。结果 Redis 内存吃满系统内存，然后被 OOM Killer 杀死，没做持久化的话数据全丢。**这本质上是把 Redis 当黑洞用，能跑全靠运气。**

## 缓存的最佳实践 Checklist

- [ ] 所有缓存 Key 都设了 TTL（且加了随机偏移量）
- [ ] 热点 Key 做逻辑过期或预热，不依赖物理 TTL
- [ ] 非法参数在入口被拦截（防穿透）
- [ ] Redis 不是单点（有主从/哨兵/集群）
- [ ] 缓存 Key 有命名规范（`项目:业务:类型:id`）
- [ ] 大 Key 被拆分或禁止（过大的 Value 禁止存 Redis）
- [ ] 写操作删缓存，不是更新缓存
- [ ] 缓存不可用时系统能降级（不是直接崩）
- [ ] `maxmemory` 和淘汰策略已设置

> **终极骚话：** 把上面这个 Checklist 贴在显示器上，比你背 100 道 Redis 面试题都有用。**面试考的是"你知道什么"，生产环境考的是"你没漏掉什么"。**
