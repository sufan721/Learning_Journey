# Redis 持久化

> **金句开篇：** Redis 的持久化是它和 Memcached 之间最深的护城河。但护城河也会决堤 —— 用好了是保险，用错了是自残。

---

## 为什么需要持久化？

Redis 是内存数据库，断电就凉。持久化就是把内存数据写到磁盘，重启时恢复回来。

> **批判时刻：** 有些人觉得"Redis 就是缓存，丢了就丢了，要什么持久化"。然后某天 Redis 挂了重启，缓存全空，所有流量直冲 MySQL，数据库当场去世。**缓存确实可以丢，但"可以丢"不等于"丢了系统还能活"。你没做降级、没做限流，就别嘴硬"缓存丢了没事"。**

---

## RDB（Redis Database）

RDB 是**快照式**持久化：在某个时间点，把内存中**所有数据**写到一个 `.rdb` 二进制文件里。

### 触发方式

| 方式 | 命令 | 特点 |
|------|------|------|
| 手动同步 | `SAVE` | **阻塞所有请求！** 主进程亲自写，生产禁用 |
| 手动异步 | `BGSAVE` | Fork 子进程写，主进程继续服务 |
| 自动触发 | `save 900 1`（配置） | 900 秒内 1 次修改就触发 |

### BGSAVE 流程

```
主进程                     子进程
   │                         │
   ├── fork() ──────────────>│
   │   (copy-on-write)       │
   │                         ├── 将此刻内存数据写入临时 RDB 文件
   │   继续处理命令...        │
   │                         ├── 写完，原子 rename 替换旧 RDB
   │                         └── 退出
   ▼
```

> **骚话：** `fork()` 是 RDB 的灵魂，也是 RDB 的命门。fork 的时候如果内存占了 20GB，即使 Copy-on-Write，页表复制本身也够你喝一壶 —— 可能造成毫秒级的阻塞。**所以大内存实例做 RDB，容易 fork 一时爽，主线程火葬场。**

### RDB 配置

```conf
# 900 秒内至少 1 个 key 变化
save 900 1
# 300 秒内至少 10 个 key 变化
save 300 10
# 60 秒内至少 10000 个 key 变化
save 60 10000

# RDB 文件名
dbfilename dump.rdb

# 当 BGSAVE 失败时，停止接受写请求（默认 yes，强烈建议别关）
stop-writes-on-bgsave-error yes

# 是否用 LZF 压缩 RDB 文件（CPU 换磁盘空间）
rdbcompression yes

# 写入完是否用 CRC64 校验
rdbchecksum yes
```

### RDB 优缺点

| 优点 | 缺点 |
|------|------|
| 单个紧凑文件，适合备份和灾难恢复 | **两次快照之间的数据会丢**（通常几分钟） |
| Fork 子进程写，主进程不 IO | Fork 本身在大内存下很重 |
| 恢复大数据集比 AOF 快 | 不是实时持久化 |

> **工程真相：** RDB 适合做**冷备**——每天凌晨自动 BGSAVE 一份传到 OSS/S3，出大事了至少能回到今天早上。把它当实时持久化用，丢数据只是时间问题。

## AOF（Append Only File）

AOF 是**日志式**持久化：把每一条**写命令**追加到 `.aof` 文件中。重启时，Redis 把 AOF 里的命令重新执行一遍，恢复数据。

### AOF 三大刷盘策略

| 策略 | 配置 | 行为 | 安全性 | 性能 |
|------|------|------|--------|------|
| Always | `appendfsync always` | 每条命令都 fsync | **最高，一条不丢** | **最差，和磁盘速度挂钩** |
| Everysec | `appendfsync everysec` | 每秒 fsync 一次 | 最多丢 1 秒数据 | 折中，**推荐** |
| No | `appendfsync no` | 交给操作系统决定 | 不可控 | 最高，但谁用谁傻 |

> **金句：** `everysec` 是 Redis 持久化策略中的黄金选择 —— 你几乎感受不到性能影响，真出事了最多丢 1 秒数据。`always` 是给那种"丢一条数据就要开除员工"的场景准备的，但大概率你的硬盘先扛不住。

### AOF 重写（Rewrite）

AOF 文件会越来越大（比如你对同一个 key INCR 了 1000 次，AOF 里有 1000 条记录），重启时重放这些命令慢得令人发指。**AOF 重写就是为了瘦身**：把对同一个 key 的多次操作合并成最终状态。

```
重写前 AOF:
SET count 1
INCR count
INCR count
...（1000 条）
SET name jack
SET name rose

重写后 AOF:
SET count 1000
SET name rose
```

#### 触发条件

```conf
# AOF 文件比上次重写后增长超过 100%
auto-aof-rewrite-percentage 100
# AOF 文件最小达到 64MB 才触发重写
auto-aof-rewrite-min-size 64mb
```

手动触发：`BGREWRITEAOF`（同样是 Fork 子进程来做）

> **批判时刻：** AOF 重写不是免费的午餐。同样是 fork()，大内存实例在重写时一样卡顿。**如果你的实例内存 32GB+，RDB 和 AOF rewrite 的时间要错开，别让两个子进程同时搞，CPU 和 IO 直接拉满，主线程卡成狗。**

### AOF 配置

```conf
# 开启 AOF（默认 no，但强烈建议 yes）
appendonly yes

# 刷盘策略，everysec 是真理
appendfsync everysec

# 重写时不刷盘（性能优化，允许丢一点数据）
no-appendfsync-on-rewrite no

# AOF 文件名
appendfilename "appendonly.aof"
```

### AOF 优缺点

| 优点 | 缺点 |
|------|------|
| 最多丢 1 秒数据（everysec 模式） | AOF 文件比 RDB 大 |
| 文件可读（文本格式），误操作后容易修复 | 恢复速度比 RDB 慢（逐条重放） |
| 自动重写，不会无限膨胀 | 高并发时 fsync 有性能压力 |

## 混合持久化（RDB + AOF）— Redis 4.0 的答案

> **骚话：** RDB 说"我恢复快但容易丢数据"，AOF 说"我恢复慢但不丢数据"。Redis 4.0 终于想通了：**你俩结婚吧。**

混合持久化 = **RDB 做全量快照 + AOF 做增量日志**。AOF 重写时，前半部分是 RDB 二进制数据（恢复快），后半部分是 AOF 日志增量（丢得少）。

### 混合持久化文件结构

```
[RDB 二进制数据] [AOF 增量命令...]
<--- 大部分数据 ---> <- 重写期间新写入 ->
```

### 配置

```conf
# 开启混合持久化（5.0 开始默认 yes）
aof-use-rdb-preamble yes
```

### 恢复流程

Redis 重启时：
1. 先检查是否有 AOF 文件（有 AOF 就优先用 AOF）
2. 如果是混合持久化文件，先加载 RDB 部分（快），再重放 AOF 部分（少）
3. 只有 RDB 文件，加载 RDB

> **结论：** 混合持久化是当前生产环境的**最佳实践**。既能快速恢复，又不会丢太多数据。**Redis 4.0 以后的版本，不开混合持久化就是跟自己过不去。**

---

## RDB vs AOF vs 混合：终极选型指南

| 场景 | 推荐方案 |
|------|---------|
| 纯缓存，丢了无所谓 | 关掉持久化，`save ""` + `appendonly no` |
| 缓存为主，丢了肉疼但不致命 | 只开 RDB，每天冷备 |
| 数据重要，不能丢太多 | **混合持久化（everysec + RDB 快照）** |
| 一条数据都不能丢 | 混合持久化 + 同步到 MySQL/PG 做主存储 |
| 金融交易核心数据 | **别用 Redis 做主存储，你不是在玩命吗？** |

> **终极金句：** Redis 的持久化再强，它也是个缓存数据库。**真正重要的数据，主存储永远是关系型数据库。Redis 是兵器库里的匕首，不是防弹衣。**
>
> 见过最离谱的操作：用 Redis 做订单表主存储，RDB 每天存一次，AOF 没开。然后服务器断电，全天订单全丢，客服电话被打爆。**不要把 Redis 当 MySQL 用，你的用户不会原谅你。**

## 大 Key 对持久化的影响

> **额外一枪：** 大 Key（比如一个 Set 里有 100 万个元素，或者一个 String 存了 50MB 的 JSON）是 Redis 的隐形杀手。

- **RDB**：fork 时大 Key 的 Copy-On-Write 会复制整个内存页，内存瞬间爆炸
- **AOF**：大 Key 操作产生巨大的 AOF 日志，重放过慢
- **主从同步**：大 Key 同步阻塞网络和从库

**解决方案：**
- 拆大 Key：Hash 用 `HSET key field` 分片；List 按日期/批次拆分
- 用 `UNLINK` 替代 `DEL`（异步删除，4.0+）
- 定时扫描：`redis-cli --bigkeys`
- 对开发：**代码 Review 时强制检查 Redis Value 大小**

> **骚话：** 大 Key == 定时炸弹。今天它能跑，明天数据量翻倍就炸。你写的 `SET user:timeline (全部 5000 条动态的 JSON)`，在产品眼里是"用户的动态列表"，在运维眼里是"凌晨 3 点的报警电话"。
