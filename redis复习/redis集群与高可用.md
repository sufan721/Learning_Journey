# Redis 集群与高可用

> **金句开篇：** 单机 Redis 就像独木桥——能走，但别指望它扛住所有人。高可用不是选择题，是生产环境的入场券。

---

## 为什么要集群？

单机 Redis 的四个致命缺陷：

| 问题 | 后果 |
|------|------|
| **单点故障** | Redis 挂了，整个缓存层失联 |
| **内存上限** | 一台机器内存有限（64GB/128GB 顶天） |
| **读写压力** | 10 万 QPS 单机能扛，100 万 QPS 呢？ |
| **网络带宽** | 一台机器的网卡吞吐量是有限的 |

> **骚话：** 单机 Redis 在开发环境跑得飞起，上了生产就变成"定时炸弹"。你永远不知道运维什么时候会打电话告诉你"那个 Redis 又挂了"——这里的"又"字，是血泪。

---

## 一、主从复制（Master-Slave / Master-Replica）

主从是 Redis 高可用的**第一块积木**。一个 Master 负责写，多个 Slave 负责读。

```
        ┌──────────┐
        │  Master  │  ← 写操作
        └────┬─────┘
     ┌───────┼───────┐
     ▼       ▼       ▼
┌───Slave──Slave──Slave──┐  ← 读操作（负载均衡）
│                        │
└────────────────────────┘
```

### 主从同步流程

#### 1. 全量同步（Full Resync）— 初次连接

```
Slave                            Master
  │                                 │
  ├─ PSYNC ? -1 ──────────────────>│  (第一次同步，不知道自己的 offset)
  │                                 │
  │<─ FULLRESYNC runid offset ──────┤  (主库返回 runid + 当前 offset)
  │                                 │
  │                            Master 执行 BGSAVE 生成 RDB
  │                                 │
  │<──────── RDB 文件 ──────────────┤  (主库把 RDB 发给从库)
  │                                 │
  │ 加载 RDB                          │
  │                                 │
  │<──── 同步期间的增量命令 ─────────┤  (存在 replication buffer 里)
  │                                 │
  ▼ 执行增量命令，追上 Master        ▼
```

#### 2. 增量同步（Partial Resync）— 断线重连

如果 Slave 断线重连，且 Master 的 `repl_backlog_buffer` 里还保留着断线期间的增量数据，就只同步断线期间的那部分，不需要全量 RDB。

```
增量同步的条件:
  Slave:  "我是 <runid>，当前 offset = 10000"
  Master: "我记得你的 runid，且 backlog 里还有 10000 之后的数据 → OK，增量同步"
  Master: "我不认识你，或 backlog 已经覆盖不了 10000 → 全量同步"
```

> **批判时刻：** `repl_backlog_buffer` 的大小决定了增量同步能不能成功。默认只有 1MB，在高并发写入下几秒钟就被冲掉了。**生产环境至少要设到 64MB 以上，否则断连几秒钟就得全量同步，大内存实例的 fork() 会让你痛不欲生。**

### 主从配置

```conf
# 从库配置
replicaof 192.168.1.100 6379
# 从库是否只读（默认 yes，别改）
replica-read-only yes
# 复制积压缓冲区大小（默认 1MB，太小！）
repl-backlog-size 64mb
# 无盘复制（直接网络传输，不先写磁盘 RDB）
repl-diskless-sync yes
```

### 主从的问题：谁来故障转移？

```
Master 挂了 →
  Slave 变成可读不可写 →
  需要人工介入：
    1. 选一个 Slave 升级为 Master
    2. 通知其他 Slave 和新 Master 同步
    3. 通知所有客户端新 Master 的地址
```

> **骚话：** 纯主从架构的致命弱点：**故障转移靠人工**。如果你凌晨三点被叫起来执行 `SLAVEOF NO ONE`，你就知道哨兵是为你而生的。

## 二、哨兵（Sentinel）

哨兵是一个**独立的进程**，负责**监控、通知、自动故障转移**。

```
       ┌──────────────┐
       │   Sentinel   │  (至少 3 个，奇数个)
       │   集群(Quorum)│
       └──────┬───────┘
    ┌─────────┼─────────┐
    ▼         ▼         ▼
┌─Master─┐ ┌Slave1┐ ┌Slave2┐
│  (写)  │ │ (读) │ │ (读) │
└────────┘ └──────┘ └──────┘
```

### 哨兵的核心任务

| 任务 | 说明 |
|------|------|
| **监控** | 定期 PING，检查 Master 和 Slave 是否存活 |
| **通知** | 节点挂了通知管理员/其他程序 |
| **自动故障转移** | Master 挂了，自动选一个 Slave 升为主 |
| **配置提供者** | 客户端通过哨兵获取当前 Master 地址 |

### 主观下线 vs 客观下线

```
主观下线 (SDOWN):
  一个 Sentinel 发现 Master 没响应 PING → 自己判定它"主观下线"

客观下线 (ODOWN):
  多个 Sentinel 都判定 Master 下线 → 达到 quorum 数量 → "客观下线"
  触发故障转移(Failover)
```

> **金句：** 哨兵的 Quorum 机制体现了分布式系统的核心智慧：**一个人的判断叫猜测，多数人的判断叫共识。** 单哨兵的网络抖动可能会误判，但三个哨兵同时抖动才是真有问题。

### 故障转移流程（Leader Sentinel 是怎么选出来的？）

```
1. 发现客观下线后，所有 Sentinel 开始投票选 Leader
2. 每个 Sentinel 给自己想支持的 Sentinel 投票（先到先得）
3. 拿到 majority（过半数）票的 Sentinel 成为 Leader
4. Leader 负责执行故障转移:
   a. 在所有健康的 Slave 中选最优的（优先级→offset→runid）
   b. 将其提升为 Master（SLAVEOF NO ONE）
   c. 其他 Slave 改从新 Master 同步
   d. 通知客户端新 Master 地址
```

### 哨兵配置

```conf
# sentinel.conf
sentinel monitor mymaster 192.168.1.100 6379 2
#              名称      Master IP   端口   Quorum(需要2个哨兵同意才客观下线)

sentinel down-after-milliseconds mymaster 5000
# 5 秒没响应就判定主观下线

sentinel failover-timeout mymaster 10000
# 故障转移超时时间

sentinel parallel-syncs mymaster 1
# 故障转移后，每次最多让几个 Slave 同步新 Master
# 设为 1：逐个同步，保证 Master 不会网络爆炸
```

> **批判时刻：** 哨兵的核心注意事项：
> 1. **至少 3 个哨兵且部署在不同机器上** — 你三个哨兵全跑在一台机器上，机器一挂全挂。
> 2. **Quorum 不能太小** — 设成 1，一个哨兵网络抖一下就能触发故障转移。
> 3. **哨兵本身也会挂** — 考虑奇数个节点（3/5/7），且跨机房/跨可用区部署。

## 三、Redis Cluster（集群模式）

哨兵解决了**高可用**，但没解决**数据量爆炸**和**超高并发写入**的问题。Cluster 把数据**分片**到多个 Master 上，每个 Master 只存一部分数据。

```
┌──────────────────────────────────────────────┐
│                 Redis Cluster                │
│                                              │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐     │
│  │Master A │  │Master B │  │Master C │     │
│  │slot 0-  │  │slot 5461│  │slot     │     │
│  │  5460   │  │ -10922  │  │10923-   │     │
│  │         │  │         │  │ 16383   │     │
│  └────┬────┘  └────┬────┘  └────┬────┘     │
│       │            │            │           │
│  ┌────▼────┐  ┌────▼────┐  ┌────▼────┐     │
│  │ Slave A │  │ Slave B │  │ Slave C │     │
│  └─────────┘  └─────────┘  └─────────┘     │
└──────────────────────────────────────────────┘
```

### Hash Slot（哈希槽）

Cluster 把整个数据空间分成 **16384 个哈希槽**：

```
slot = CRC16(key) % 16384

例如:
  CRC16("user:1001") % 16384 = 2345  → 这个 Key 存在负责 slot 2345 的 Master 上
  CRC16("order:5002") % 16384 = 12100 → 这个 Key 存在负责 slot 12100 的 Master 上
```

> **骚话：** 16384 这个数字有讲究。太大了，心跳包携带 slot 信息会很重（全量 slot 信息是 16384 / 8 = 2KB）；太小了，数据分布不均匀。**16384 是不大不小的黄金数字，是 antirez 的工程直觉。**

### MOVED vs ASK 重定向

```
客户端向 Master A 请求 user:1001:
  slot = CRC16("user:1001") % 16384 = 2345

如果 Master A 不负责 slot 2345:
  返回: MOVED 2345 192.168.1.101:6379
  客户端: 更新本地 slot 映射，重定向到 Master B

如果是 slot 迁移过程中:
  返回: ASK 2345 192.168.1.101:6379
  客户端: 临时重定向到 Master B（不更新本地映射）
```

| 重定向 | 含义 | 客户端行为 |
|--------|------|-----------|
| **MOVED** | slot 永久属于另一个节点 | 更新本地 slot 表，永久走新节点 |
| **ASK** | slot 正在迁移中 | 仅当次请求走新节点 |

### Cluster 节点通信：Gossip 协议

Cluster 节点之间通过 Gossip 协议交换信息，**去中心化**，没有中心节点。

```
每个节点定期随机 PING 几个其他节点，交换信息:
  - 自己负责的 slot
  - 自己知道的其他节点状态
  - 新加入的节点

优点: 去中心化，任意节点挂了不影响集群
缺点: 信息传播有延迟（最终一致性）
```

### Cluster 配置

```conf
# 开启集群模式
cluster-enabled yes

# 集群配置文件（自动生成，不用手动编辑）
cluster-config-file nodes.conf

# 节点超时时间（超过此时间没收到 PONG 就认为节点挂了）
cluster-node-timeout 15000

# 从节点迁移（有节点挂了，其 Slave 自动迁移到其他 Master）
cluster-migration-barrier 1

# 集群是否需要所有 slot 都有节点负责才能提供服务
cluster-require-full-coverage yes
```

### Cluster 的坑与限制

| 限制 | 说明 | 应对 |
|------|------|------|
| **批量操作跨 slot** | `MSET`/`MGET` 如果 Key 不在同一个 slot，报错！ | 用 `{}` Hash Tag 强制同 slot |
| **事务跨 slot** | 事务里的 Key 必须在同一个 slot | Hash Tag |
| **Lua 脚本跨 slot** | 同上 | Hash Tag |
| **只能用一个数据库** | Cluster 只支持 db0（`SELECT` 被禁用） | 接受它，多 db 本就是反模式 |
| **Pub/Sub 广播到所有节点** | 发布的消息会广播到集群所有节点 | 量太大就别用 Cluster 做 Pub/Sub |

### Hash Tag：强制 Key 落到同一个 slot

```bash
# 这两个 Key 会落在同一个 slot
user:{1001}:name
user:{1001}:age

# slot 计算时只用 {} 里的部分
slot = CRC16("1001") % 16384
```

> **批判时刻：** Hash Tag 是解决跨 slot 问题的银弹，但也是双刃剑。如果过度使用，把所有 Key 都塞到 `{同一个tag}` 下，就相当于把 Cluster 退化成了单机。**数据分布不均匀 → 热点 Master → 集群的意义就没了。** Hash Tag 要克制，只对真正需要批量操作的 Key 用。

## 四、三种架构终极对比

| 维度 | 主从 | 哨兵 | Cluster |
|------|------|------|---------|
| 读写分离 | ✅ | ✅ | ✅ |
| 自动故障转移 | ❌ 靠人工 | ✅ | ✅（内置） |
| 数据分片 | ❌ 全量数据 | ❌ 全量数据 | ✅ 分片存储 |
| 可扩展性 | 垂直 | 垂直 | **水平** |
| 运维复杂度 | 低 | 中 | **高** |
| 客户端要求 | 简单 | 需支持哨兵协议 | 需支持 Cluster 协议 |
| 适用规模 | 开发/小项目 | 中小项目 | **中大型项目** |

### 选型建议

```
数据量 < 10GB，QPS < 5万:
  → 哨兵（3 节点）就够了，别上 Cluster 自找麻烦

数据量 > 100GB，QPS > 10 万:
  → Cluster 走起，水平扩展是唯一出路

数据量在 10GB~100GB 之间:
  → 先上哨兵，同时做好迁移到 Cluster 的准备
```

> **金句：** 架构选型的黄金法则 —— **够用就好，不要过度设计。** 日活 100 的产品上 Cluster，不是有远见，是闲得慌。日活 1000 万还在用单机，不是省钱，是在赌命。

## 五、高可用的最后一道防线：客户端

不管你 Redis 集群多完美，客户端写烂了照样崩。

### 客户端应该做的事

| 能力 | 说明 |
|------|------|
| **连接池** | 别每次请求都新建连接 |
| **重试机制** | MOVED/ASK 重定向自动处理 |
| **熔断降级** | Redis 不可用时，返回默认值或直接 fail fast |
| **本地缓存** | 极端情况下，用本地 Caffeine/Guava 缓存兜底 |
| **连接健康检查** | 定期 PING，剔除死节点 |

### Java 客户端选型

| 客户端 | 状态 | 特点 |
|--------|------|------|
| **Jedis** | 老牌，稳定 | API 直观，但连接池是同步的，Cluster 模式需 JedisCluster |
| **Lettuce** | Spring Boot 默认 | 异步/响应式，天然支持 Cluster + 哨兵 |
| **Redisson** | 分布式利器 | 提供分布式锁/集合/队列等高级 API |

> **骚话：** 如果你用 Spring Boot + Redis，大概率已经在用 Lettuce 了（Spring Boot 2.x 默认）。但很多人不知道 Lettuce 的连接是**异步的**，在 Cluster 模式下可能出现"命令发到了错误的节点"而不报错的问题。**别光用默认配置，花半小时读下文档，能省下未来三天的排查时间。**

## 总结：Redis 高可用的三层金字塔

```
         ┌──────────┐
         │ 客户端    │ ← 熔断、降级、重试、本地兜底
         │ 保护层    │
        ┌┴──────────┴┐
        │ 高可用层    │ ← 哨兵/Cluster，自动故障转移
        │            │
       ┌┴────────────┴┐
       │ 数据冗余层    │ ← 主从复制，一主多从
       │              │
      ┌┴──────────────┴┐
      │  持久化基础     │ ← RDB + AOF 混合持久化
      └────────────────┘
```

> **终极金句：** 高可用不是加一台机器就能解决的，它是一层一层叠出来的铠甲。**你缺了任何一层，压力就会传导到下一层，直到那个凌晨三点的报警电话响起。**
>
> 同理，面试官问"你们系统怎么保证 Redis 高可用"，别只回答"用了 Cluster"。把这三层金字塔画出来，**面试官就知道你是真正在生产环境扛过事的人，不是背八股文的。**
